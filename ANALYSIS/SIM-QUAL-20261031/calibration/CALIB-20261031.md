两种取值规则都自洽：**"带中心"**（本文 §0 表：A=70、B=150）与**"带上沿"**（已提交合同：A=90、B=160）。差别只是设计意图（"典型轻载" vs "带内最不利点"）。已提交合同采用后者；本报告的实测值**同时支持**这两种选择，逐 cell 数值见 §2 —— **不需要重跑，只需在预注册里写清用的是哪条规则**。

三条必须同时知道的结论：

1. **这份场景只有一个瓶颈走廊，不存在"全局利用率"。** 所有 10 个 cell 的 ρ_p50 都在 0.02–0.07、ρ_p90 0.14–0.45，只有 `isl:128:127` / `isl:127:126` 这一对（tokyo→singapore 路径上的两跳）达到 0.43–0.89。**档位定义只能按瓶颈链路（ρ_max）**，任何"全局平均利用率"都会把 A/B/C 压成同一个数。
2. **C 档在这个合同里不可达。** 最高负载 165 Mbps 的实测 ρ_max 只有 **0.891**，且曲线在高端变平（斜率从全段 0.00435/Mbps 降到 160→165 段的 0.00277/Mbps）。线性外推给 174/185/186 Mbps（三种拟合法），但**凹曲线意味着真实需求只会更高（≈185–200+）**，不能当结论用。
3. **A=90 的余量只有 0.001**（ρ_max 0.599 vs 带上限 0.60）：它不是"轻载的安全点"，而是"A 的上边界"。若 Round-3 要区分 A 的两种解释，建议预注册时写明 A=90 属于"带内最不利"，并在结果里同时报 70/90 两个点的对照（同一 policy，额外 2 run ≈ 4 min）。
4. **没有任何一条链路达到 ρ≥0.90**（10 个 cell 全部 `links_ge_090 = 0`），也没有任何 cell 出现 ρ≥1（`saturation_scan.any_cell_rho_max_ge_1 = false`）。所以本轮数据**不含真正的饱和样本**，B 档是"接近但未饱和"，C 档缺失。

## 1. 方法（口径写死，便于复算）

对每个 cell，只读回传产物的 `arms/now/result.json.gz`，在 **[4.0, 14.0) s** 窗口内按**定向** ISL 计算：

```
served_bits  = Σ 该有向链路窗口的 served_bits × 落在窗口内的比例（跨边界按比例分摊）
lambda       = served_bits / 10 s                      [bit/s，报告另给 Mbps]
mu           = 该链路窗口记录的 rate_bps（恒定速率场景 = 100 Mbps）
rho          = lambda / mu
epsilon      = mu - lambda                             [报告给 Mbps，即剩余容量]
```

- 只统计**窗口内真正承载过服务的定向 ISL**（每个 cell 217–274 条；140 sat/7 plane 在 `max_isl_km=3000` 下的 364 条有向 ISL 中，其余在该窗口内没有服务事件）。因此 ρ 分布是"活跃链路"分布，**不是全网 364 条**的分布；要全网分布必须把空闲链路按 ρ=0 计入，那会把 p50 拉到 0，对本用途没有信息量。
- `mu` 取该链路窗口的众数速率并同时记录 `rate_values_bps`（是否恒定）；本场景 `rate_model=constant`，全部链路 `rate_uniform=true`。
- 窗口 10 s，含 4–8 s 预热后的稳定段与 8–8.5 s 的 pulse（仅 pf cells 有 pulse；cal-* 无 pulse）。

## 3. ρ(load) 与 A/B/C 建议

`ρ_max(load)` 在 60–165 Mbps 上升 0.433→0.891，全程单调（无异常点），但**斜率递减**：

| 区间 | Δρ / Δload |
|---|---|
| 60→120 | 0.0050 /Mbps |
| 120→140 | 0.0042 /Mbps |
| 140→165 | 0.0029 /Mbps |
| 全段拟合 | ρ = 0.1943 + 0.004348·load |

- **A（0.40–0.60）→ 70 Mbps**：带内实测有 `cal-060/070/080/090`（0.433/0.482/0.543/0.599），取离带中心 0.50 最近者 = `cal-070`（0.482，偏差 0.018）。若希望"A 的偏高端"可用 90 Mbps（0.599，贴带上沿）。
- **B（0.80–0.90）→ 150 Mbps**：带内实测有 `cal-140/150/160`（0.818/0.846/0.877），取离中心 0.85 最近者 = `cal-150`（0.846，偏差 0.004）。B 的可用余量：top 链路 ε=15.4 Mbps。
- **C（0.95–0.99）→ GAP**：无任何 cell 落在带内，最高 0.891（165 Mbps）。三种线性外推给 `0.95` 的负载估计分别是 **173.8（全段拟合）/184.9（140–165 拟合）/186.3（末段两点）**，`0.99` 对应 183.0/198.4/200.7。**由于曲线凹（高端变平），这些是下界，不是义务值。** 建议要么（a）**新增 `cal-180`、`cal-190` 两个 cell 实测**（改合同 → 一次新 commit + publish + 2×~300 s，成本很低），要么（b）明确把 C 档改定义为"接近饱和（0.85–0.90）"并在报告里写明未达 0.95–0.99 —— **不得**把 186 Mbps 当作实测值使用。

## 4. D（突发）baseline 建议

**baseline = 140 Mbps（`cal-140`，实测 ρ_max 0.818 / p90 0.353）+ pulse `{start_s 8.0, duration_s 0.5, multiplier 1.6}`。**

理由（按重要性）：
1. 突发档必须**从不饱和的 baseline 起跳**，否则 pulse 前后都在队列受限区，瞬态不可识别。140 Mbps 的瓶颈还有 18.2 Mbps 余量（ε=18.2），是 B 带内**最靠近还能被 1.6× 打穿**的点。
2. 线性外推的瞬时 ρ_max ≈ 0.818×1.6 = **1.31**（这只是标度估计，不是实测）：瓶颈会在 0.5 s 内进入队列累积，随后 drain 回 0.818，形成"可测的上升-回落"形状。
3. 若更看重**与 Round-1 的可比性**，Round-1 用的 baseline 是 120 Mbps + ×1.6（瞬时 ≈1.17）；两者都可，但**必须在预注册里固定一个**，不能事后挑。150/160 Mbps 不推荐：×1.6 后瞬时 ≈1.35/1.40，drain 回到的 baseline 已经太接近饱和，pulse 与 baseline 效应会混在一起。

## 6. 限制与缺口（写在结论旁边的）

1. **C 档无实测样本**（§3）：0.95–0.99 目标未被任何 cell 达到，这是本轮最重要的缺口。要么补 `cal-180`/`cal-190`，要么把 C 档重新定义并写明。
2. **ρ 分布只在"活跃链路"上统计**：每 cell 有 217–274 条定向 ISL 承载过服务，其余在该窗口内完全空闲。若 Round-3 需要"全网利用率"，必须显式把空闲链路计入（ρ=0），本报告没有这样做。
3. **ρ_p90 不单调**（`cal-070` 0.215 → `cal-080` 0.144，`cal-090` 0.211 → `cal-100` 0.187）：因为每个 cell 的**活跃链路集合不同**（217–262 条），p90 是"这些链路的第 90 百分位"，不是同一集合的同一分位。因此 p90 **不用于**档位判定，只作参考；档位判定只用 ρ_max（同一物理瓶颈链路，跨 cell 可比）。
4. **无 pulse 的 cal cell 与有 pulse 的 pf cell 不可直接比 ρ**：cal-* 无 pulse，pf-* 有 8.0–8.5 s ×1.6。本报告的 ρ 表只含 cal-*。
5. **单 seed、单轨迹**：全部 cell `trace_program.seed=7`。ρ(load) 的点估计没有跨 seed 误差棒；若档位边界重要（例如 A 的 0.599 贴 0.60），应补一个 seed 复核。
