# 参考项目里，哪些设置该抄、哪些该算、哪些只能试

> 2026-10-19 ｜ 对象：SatCom-TELMA/MA-DRL_Routing_Simulator（本机 /tmp/madrl 逐行读码）
> 用途：给你一份"不用拍脑袋"的参数决策表。每个值都标了**出处**和**依据类型**。

---

## 0. 先给一条元规则（以后所有参数都这么处理）

拿到任何一个参数，先问一句：**它和我研究的问题耦合吗？**

| 判断 | 处理方式 | 例子 |
|---|---|---|
| 不耦合：物理常数、协议标准、器件参数 | **闭眼抄**，不要自己发明 | 光速、DVB-S2X 表、26 GHz/500 MHz/10 W、包长 64.8 kbit |
| 强耦合：和"我要证明什么"直接相关 | **推导**，用公式从目标反解 | 星间速率、包长、缓冲、负载、预测跨度 |
| 两者都不是：纯经验、无闭式解 | **扫描**，报敏感性，不报单点 | 广告周期、队列阈值、扫描档位 |

**拍脑袋的反面不是"想清楚"，是"能说出这个值由什么决定"。** 说不出来，就说明它属于第三类，应该做扫描而不是选一个数。

## 2. 第二类：推导（这才是你真正要设的 7 个数）

七个参数，五个公式，全部可以手算。设完就没有"拍脑袋"了。

### 2.0 五个公式

    (1) 传播      τ_prop = d / c                        d=斜距，c=3.34 µs/km
    (2) 发送      τ_ser  = L_pkt / C                     L=包长，C=链路速率
    (3) 排队      τ_queue = ρ/(2(1-ρ)) · τ_ser           M/D/1 平均等待
    (4) 缓冲      Q_buf  = k · C · RTT，k = 2–8          BDP 的倍数
    (5) 负载      offered = ρ · C / η                     η=拓扑摊开系数（实测）

### 2.1 包长 L：抄 64 800 bit

理由：这是 DVB-S2 的一帧，也是参考项目的最小传输单元。改成 1 Mbit 等于把"包"变成了"流块"，和文献不可比。
**只有在一种情况下改**：你想做"小包路由"，那时用 8 000 bit（控制面已经是这个量级）。

### 2.2 链路速率 C：由 R1 ≤ 0.1 反解

    τ_ser / τ_prop ≤ 0.1  →  C ≥ L_pkt / (0.1 · τ_prop)

以 2000 km（τ_prop = 6.7 ms）、L = 64 800 bit 代入：

    C ≥ 64 800 / (0.1 × 6.7 ms) ≈ 97 Mbps

**结论：C ≈ 100 Mbps**。这就是"发送时间占比不超过 10%"的最低速率，不是拍的。
如果你想要更"光学"的手感，取 1 Gbps，R1 = 0.01；但那样队列在 ρ<0.95 时几乎不动（见 2.5）。

### 2.3 缓冲 Q_buf：由 BDP 反解

    BDP = C × RTT ≈ C × 2·τ_prop
    Q_buf = (2–8) × BDP

100 Mbps、RTT 13.4 ms → BDP = 1.34 Mbit → **Q_buf = 3–11 Mbit，取 8 Mbit（约 6×BDP）**。
你现在的 256 Mbit 是 BDP 的 **190 倍**（按 100 Mbps 算）或 2560 倍（按 10 Mbps 算）。
后果：丢包几乎不发生、排队时延能到秒级、队列占用率永远是"满"或"空"两极。

> k 为什么取 2–8：太小会因突发丢包（k=1 时一个 burst 就打满），太大就是 bufferbloat。2–8 是工程惯例区间，属于"有依据的经验值"，可以接受。

### 2.4 负载 offered：由 ρ 反解，但 η 必须实测

    offered = ρ_target · C / η

η 是"拓扑摊开系数"——同样的 offered 摊到多少条并行链路上。你仓库里实测过：24 星/3 面、C=10 Mbps 时

    util_max ≈ 0.0235 × offered_mbps     →  η ≈ 0.0235

**这个数不是物理常数，是拓扑属性。** 卫星越多、路径越密，η 越小；走廊越窄，η 越大。
所以正确顺序是：**先定拓扑让 η 变大，再用 offered 微调**，而不是反过来用 offered 硬顶。

### 2.5 热点链路利用率 ρ：由"排队要能被看见"反解

要让每跳排队达到传播时延的 0.2–2 倍：

    ρ/(2(1-ρ)) · R1 ∈ [0.2, 2]

R1=0.1 时 → ρ ∈ [0.8, 0.95]；R1=0.01（1 Gbps）时 → ρ ∈ [0.98, 0.995]，现实中做不到。
**所以 1 Gbps 的链路在仿真里根本不会排队——这不是你调参能解决的，是物理。**

### 2.6 预测跨度 Δ：由服务时间和状态年龄共同决定

    Δ ≥ 5 · τ_ser        （否则队列还没动）
    Δ ≈ 0.5–2 × 状态年龄   （否则"补到现在"吃掉全部收益）

C=100 Mbps、L=64.8 kbit → τ_ser=0.65 ms → Δ ≥ 3.2 ms；若广告周期 200 ms，则 Δ ≈ 100–400 ms。
**你现在 Δ=50–80 ms，τ_ser=100 ms，两条都不满足。**

### 2.7 仿真时长 T：由预热和统计量决定

    T = T_warm + T_eval
    T_warm ≥ 10 × 最大队列排空时间 ≈ 10 × (Q_buf / C)
    T_eval  ≥ 5000 个包 / 到达率

100 Mbps、8 Mbit 缓冲 → 排空 80 ms → 预热 ≥ 0.8 s；12 Mbps 到达率 → 5000 包需 27 s。
**所以 T ≈ 30–60 s 起步，不是你现在的 300 s。** 300 s 不是错，是"没必要且算得慢"。

## 3. 第三类：参考项目本身有问题，**不要抄**（6 条）

这一节比前两节更重要。抄错的地方，比不抄更糟。

| # | 参考项目的做法 | 问题 | 你该怎么做 |
|---|---|---|---|
| 1 | `input.csv` 里 **Fraction = 1.0** | 负载 = 接入容量，压力来自上行/下行，不是星间。你测"星间路由"，结果瓶颈在接入 | 用 §2.4 反解 offered，并跑 `scene_check` 确认不是 ACCESS_LIMITED |
| 2 | **队列无上限**（`quota=500` 定义了但从未使用；论文写 Qmax） | 代码与论文不一致；实际是无限缓冲 → 时延无上界 | 显式设 `isl_queue_bits`，取 2–8×BDP，并记录丢包 |
| 3 | **链路预算过于理想**（无干扰、无雨衰、无指向误差） | 2.95 Gbps 是理论上限，不是可实现速率 | 照抄模型，但结论里写明"理想链路"；或加 3–6 dB 余量做敏感性 |
| 4 | **测试时长 1–2 s，且拓扑静止**（`movementTime = 10 h`，注释明说"1–2 秒不值得移动"） | 只能测瞬态，测不到稳态；你的"预热段污染"教训同源 | 用 §2.7 定时长，至少跨 3–5 个拓扑重算周期 |
| 5 | **遍历 2–18 个网关，但不报方差、不报 seed** | 单条曲线，无法判断差异是否显著 | 至少 5 个 seed，报配对差和 CI |
| 6 | **状态把队列量化成 10 档、>5000 视为无限**（`infQueue=5000`） | 直接借这个状态定义，预测精度会被量化误差吃掉 | 预测用连续值（bit），只在喂给 DRL 时再量化 |

还有一条不算错但要留意：参考项目的**传播时延按"发送时刻的距离"算**，而不是到达时刻。卫星在 10 ms 内移动几十米，影响可忽略，但要在方法里写清楚。

## 4. 第四类：参考项目没有，必须你自己定（5 项）

这些是"你的研究问题"带来的新参数，文献里没有现成值。**给默认值 + 扫描范围 + 敏感性**，就是正确做法。

| 参数 | 参考项目 | 建议默认 | 扫描范围 | 为什么是这个默认 |
|---|---|---|---|---|
| 状态广告周期 | 无 | **200 ms** | 50 / 100 / 200 / 500 / 1000 ms | 要小于预测跨度一个量级，又不能把控制面压垮 |
| 可见范围 vis_k | 无（DRL 看 4 邻居） | **2 跳** | 1 / 2 / 3 | 2 跳是"比邻居多一点"的最小增量 |
| 预测跨度 Δ | 无 | **200 ms** | 50 / 100 / 200 / 400 ms | 由 §2.6 推得；保留 50–80 作为"短跨度对照" |
| 队列阈值（判"拥塞"） | infQueue=5000 | **1 个 BDP** | 0.5 / 1 / 2 BDP | 队列超过一个 BDP 就说明排队已超过传播 |
| 时间对齐策略 | 无 | **candidate** | stale / now / common / candidate | 四臂本来就是你的自变量 |

## 5. 如果你只改 5 个参数（最小可行方案）

按"改动小、收益大、理论站得住"排序：

| 优先级 | 参数 | 从 | 到 | 一句话理由 |
|---|---|---|---|---|
| 1 | `demand.packet_bits` | 1 000 000 | **64 800** | 恢复"包"的物理含义，R1 从 15 降到 0.1 |
| 2 | `links.isl_queue_bits` | 256 000 000 | **8 000 000** | 消掉 25 秒的 bufferbloat |
| 3 | `links.isl_rate_mbps` | 10 | **100** | 发送时间占比 ≤10% |
| 4 | `demand.offered_mbps` | 12 | **按 §2.4 反解**（先扫描） | 让热点 ρ 到 0.85–0.95 |
| 5 | `scenario.duration_s` | 300 | **60–120** | 够稳态、算得快、包数不爆 |

改完这五个，你的场景从"C：100 ms 一个包"变成"B：0.65 ms 一个包"，50–80 ms 的预测跨度才第一次有意义（相当于 80–120 个包的演化）。

> 如果你**不想动速率**（想保留 10 Mbps），那就把包长改成 **8 000 bit**：τ_ser=0.8 ms，R1=0.12，同样成立，而且只改一个参数。代价是包数涨 125 倍，时长要压到 60 s 左右。

## 6. 一张可以直接用的 YAML（基于你现有的 t1_pressure_corridor_v2）

```yaml
scenario:
  duration_s: 90          # §2.7：预热 20 s + 评估 70 s
  time_step_s: 0.1
  num_satellites: 24
  num_planes: 3
  min_elevation_deg: 5

demand:
  mode: uniform           # 先用 uniform 标定，再换 mlab/hotspot 做压力
  offered_mbps: 12        # 占位，按 §2.4 扫描后替换
  packet_bits: 64800      # ① 关键改动

links:
  rate_model: constant
  isl_rate_mbps: 100.0    # ② 关键改动（R1=0.097）
  isl_queue_bits: 8000000   # ③ 关键改动（≈6×BDP）

control_plane:
  enabled: true
  advertise_interval_s: 0.2   # ④ 与 Δ 同量级
  ttl_s: 10
  vis_k: 2

execution:
  max_packets: 200000
```

改完先跑 **E0 体检**（把十条判据算一遍），再跑 **E1 标定线**（offered 扫描，重画 `util ≈ k × offered`）。这两步不做，后面所有结论都不成立。

## 7. 三条自检：确认你没有在拍脑袋

1. **能不能用一句话说出这个值的来源？**
   - "抄的，出处是 X" → 合格
   - "算的，公式是 Y，代入得 Z" → 合格
   - "感觉差不多" → 不合格，去做扫描
2. **改这个值，结论会不会反过来？** 会 → 它必须进敏感性分析，不能只报一个点。
3. **这个值在参考项目/文献里出现过吗？** 出现过 → 优先用它的；没出现过 → 要么推导，要么明确标"自定"。

## 8. 一页速查

| 类别 | 数量 | 处理 |
|---|---|---|
| 闭眼抄 | 23 项（物理/协议/器件/星座/包结构） | 不要改，改了就不可比 |
| 推导 | 7 项（L, C, Q_buf, offered, ρ, Δ, T） | 五个公式，手算 |
| 别抄 | 6 项（Fraction=1、无队列上限、理想预算、1–2 s、单种子、10 档量化） | 参考项目的坑 |
| 自定 | 5 项（广告周期、vis_k、Δ、队列阈值、对齐策略） | 默认值 + 扫描范围 |
| 只改 5 个 | packet_bits / queue_bits / rate / offered / duration | 最小可行 |

> 一句话：**标准照抄，耦合推导，经验扫描。** 你不需要懂这个领域，你需要知道每个数由什么决定。
