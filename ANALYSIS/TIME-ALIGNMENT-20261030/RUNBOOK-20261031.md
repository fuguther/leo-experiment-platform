## 1. Tool surface: exact flags, defaults, refusals

The three `*.sh` files are **bash wrappers** (despite living next to `release_protocol.py`); all logic is in
`CODE/scripts/remote/release_protocol.py` (1718 lines). `--help` outputs below are [V] (run locally, exit 0).

### 1.1 `CODE/scripts/remote/publish-release-remote.sh`

```
Usage:
  scripts/remote/publish-release-remote.sh --commit FULL_40_CHARACTER_SHA
```
- Flags: `--commit <40-hex>` (required), `--help`. No other flags. [V]
- Env overrides (defaults): `LOCAL_WORKSPACE_DIR_OVERRIDE` (default = worktree root), `T1_REMOTE_HOST=vm`,
  `T1_REMOTE_ROOT=/data/论文/leo-t1-wt` (must stay exactly this), `SSH_BIN=/usr/bin/ssh`,
  `PYTHON_BIN=python3`, `T1_REMOTE_PYTHON=python3`. [V]
- Expected repository identity is hard-coded: `fuguther/leo-experiment-platform` [V].
- stdout on success (exact keys; parse them, do not guess the release id): [V, code]
  ```
  release_id=<40hex commit>-<64hex source_tree_sha256>
  source_git_commit=<40hex>
  remote_backup_status=verified|remote_backup_pending
  remote_install={"status":"published"|"already_present", ...}
  remote_incoming={"status":"cleaned_after_verified_publish", ...}
  ```
- Refusal conditions (all `exit 2`, message on stderr) [V, code]:
  - `--commit` must be a **lowercase full 40-char** SHA; unknown args rejected.
  - `T1_REMOTE_ROOT` must remain `/data/论文/leo-t1-wt`; ssh binary must exist; local path must be a Git checkout.
  - builder (`release_protocol.py build`, lines 505-566): commit must resolve to the full SHA; `HEAD` must equal it;
    `git status --porcelain=v1 --untracked-files=all` must be empty → `source Git worktree is dirty; release build refused`;
    branch must be a **named** branch (no detached); origin must be a GitHub `owner/repo` without embedded credentials and
    match the expected repo; no submodule/gitlinks; no tracked credential paths; secret scan must pass;
    bundle output dir must be new/empty.
  - `remote_backup` is **not** a hard refusal: if `git ls-remote --heads origin` shows **no branch tip equal to the
    commit**, the envelope records `remote_backup_status = remote_backup_pending` (reason: "no advertised origin branch
    points to this exact commit") and the release still installs (marked development/diagnostic only). If `ls-remote`
    itself fails, also `remote_backup_pending` ("live remote refs could not be verified"). [V, code lines 240-270]
  - VM side: `prepare-incoming` refuses when `releases/incoming/<release-id>.partial` already exists
    ("release incoming attempt already exists; preserve it for inspection"); `install` verifies the bundle, the uploaded
    `release_protocol.py`/`deployment_guard.py` bootstraps, and the file manifest; on failure the partial is retained;
    installing an existing id with a different artifact → `release ID collision`; identical artifact → `already_present`. [V, code]
- Install target: `/data/论文/leo-t1-wt/releases/<release-id>` (read-only tree, mode 0555 at root) [V].

### 1.2 `CODE/scripts/remote/run-release-remote.sh`

```
Usage:
  run-release-remote.sh --release-id ID --run-id ID --mode diagnostic|development \
      [--config RELEASE_RELATIVE_PATH] [--input NAME=VM_PATH]... [--seed N] \
      [--resource-group NAME] [--timeout-seconds N] -- python3 ARGS...
```
- Flags (all [V] from wrapper + parser): `--release-id`, `--run-id`, `--mode` (required),
  `--config` (optional, **release-relative safe path**: not absolute, no `..`), `--input NAME=VM_PATH` (repeatable),
  `--seed` (int), `--resource-group` (lock name), `--timeout-seconds` (default **1800**, injected into the remote call;
  `_drain_child` clamps to 1..**7200**), `--` then the target `python3 ...` argv (required).
- Defaults: `T1_REMOTE_HOST=vm`; `T1_REMOTE_ROOT=/data/论文/leo-t1-wt`; remote interpreter
  `T1_REMOTE_RUN_PYTHON=/data/论文/leo-t1-wt/envs/t1-linux-aarch64-py311-pkgset-v1/bin/python` [V].
- The wrapper invokes `<remote-python> <release>/CODE/scripts/remote/release_protocol.py run ...` and passes the target
  argv after `--`. The runner **replaces argv[0] with its own interpreter** (`sys.executable`) and records that in
  `run-manifest.json["argv"]`. [V, code]
- Refusals [V, code]:
  - `invalid full release ID` (must be `40hex-64hex`), `invalid run ID` (`^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`),
    `mode must be diagnostic or development; formal is not accepted here`,
    `command must begin with python/python3 and a CODE script or CODE module in the release`,
    `config must be a safe path relative to the immutable release`, `each input must use NAME=VM_PATH`,
    `timeout must be an integer`, `seed must be an integer`.
  - Before creating the run dir: release must be installed and verify; **runtime identity contract must match**
    (see §1.4) → `runtime identity mismatch: python|platform|machine|installed_packages_sha256` or
    `runtime dependency lock mismatch: <lock path>`; release id in envelope must match;
    `run ID already exists; IDs are never reused`; `resource group is already in use` (non-blocking flock).
  - Child process `cwd` = the **read-only release dir** → any relative output path fails with
    `PermissionError: [Errno 13]` (observed, §2.3).
  - On timeout: SIGTERM at deadline, SIGKILL +5 s, manifest `status=timed_out`, `child_output.timed_out=true`. [V, code]

### 1.3 `CODE/scripts/remote/pull-release-results-remote.sh`

```
Usage:
  pull-release-results-remote.sh --run-id ID --release-id ID --evidence-root ABSOLUTE_PATH
```
- Flags: all three required. `--evidence-root` must be an **absolute path outside the source repo** [V, code].
- Behavior [V, code]: verifies the VM receipt first (`verify-run`: terminal status, manifest/receipt hashes, file set,
  config/input snapshot identity), then streams exactly one `tar -czf` of `<runs>/<run-id>`, stages it in
  `<evidence-root>/.incoming/<run-id>.partial`, validates again, quarantines any stale partial, atomically renames to
  `<evidence-root>/<run-id>`, chmods 0555, then appends one row to `ANALYSIS/DEPLOYMENT-INDEX.jsonl`.
- Idempotent: if `<evidence-root>/<run-id>` already exists and verifies → `{"status":"already_verified",...}` and **no
  duplicate index row**; same run-id with different evidence → `deployment index already contains this run ID with
  different evidence` (exit 2, partial stays quarantined). [V, code]
- Index row schema (exact) [V, code + observed rows]: `{run_id, release_id, receipt_sha256, pullback_status:"VERIFIED",
  execution_class, analysis_commit:null, evidence_uri:"evidence://t1/<run-id>"}`.

not a later HEAD).

### 4.2 When a new publish is unavoidable

Publish a new commit if any of these is true:
1. a scenario/analysis task adds or edits **any file under `CODE/`** — e.g., a new load-bracket contract JSON, a new
   profile, a `--offered-mbps`-adjacent code change, or a bug fix. The immutable release only contains committed files [V, code];
2. the pilot needs a config/data file that is not in the `d5dcb1c` release (check with
   `ls /data/论文/leo-t1-wt/releases/<rid>/CODE/...` before launch);
3. the Lead wants the evidence row to cite `63664f3` (HEAD) rather than `d5dcb1c`.

If none applies, **no publish** — go straight to §5(c).

### 4.3 Does publish require the commit pushed to GitHub? Is `63664f3` pushed?

- **Hard requirement: no.** An unpushed commit still builds and installs; the envelope records
  `remote_backup_status=remote_backup_pending` and the release is only for development/diagnostic use. [V, code]
- **Protocol requirement: yes.** AGENTS.md §3 and the script docstring require an immutable release from a
  committed + pushed clean commit; `remote_backup=verified` is the evidence of that. [V, docs+code]
- `63664f3` **is pushed**: `git ls-remote --heads origin` →
  `63664f3adddedfb9e316397af29b16f9aab73a41 refs/heads/night/time-exp-20261031`; `origin/main` is `a0904ad…` (different,
  and irrelevant — the check accepts **any** advertised origin branch). [V]
- Note: the branch has **no local upstream configured** (`git rev-parse @{u}` fails), so `git status -sb` will not show
  ahead/behind; use `git ls-remote` for the pushed check. [V]
- If publishing `d5dcb1c` again: it is an ancestor, not a branch tip, so a **new** publish of `d5dcb1c` would be
  `remote_backup_pending`. The already-installed `d5dcb1c` release keeps the `verified` status recorded at its publish
  time. [V]

### 4.4 Release-id format and how to obtain it

- Format: `^[0-9a-f]{40}-[0-9a-f]{64}$` = `<source_git_commit>-<source_tree_sha256>` [V, code].
- The 64-hex part is **not** the Git tree hash: it is
  `sha256(canonical_json({"files":[{path,size,sha256}, …]}))` over the deployed file records
  (`deployment_guard.tree_sha256`). Example: `d5dcb1c` release suffix `87c7f2f1…` ≠ git tree `511a2e4b…` [V].
  ⇒ Do **not** precompute it by hand; read it from publish stdout line 1 `release_id=…`.
- `remote_install` tells you whether this was a fresh `published` or an idempotent `already_present`.
