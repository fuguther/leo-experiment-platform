## 11. E3 可执行性核查（2026-09-25T01:15+08:00，owner 授权后执行）

### 11.1 关键发现：状态对齐机制必须用 capacity 策略才可能显现

平台共有六个策略（config.py:236-238）：hop / delay / capacity / oracle / info_queue / info_physical。核查各自消费的信息：

| 策略 | 是否消费邻居广告状态 | 依据 |
|---|---|---|
| hop | 否（纯拓扑，单位代价 BFS） | routing.py:233-238, 291-292 |
| info_queue | 否（只用**本星自己的**出口队列 own_queue_bits） | routing.py:293-296 |
| info_physical | 否（本星队列 + 本跳距离/可用性/速率） | routing.py:297-307 |
| delay | 部分（消费 cache 的 isl_propagation_s） | routing.py:243-246, 211-231 |
| **capacity** | **是**：消费 cache 的 **isl_queue_bits**（带 TTL、peer 匹配、跳数限制；未知队列按 inf 失败关闭） | routing.py:247-279（特别是 256-270） |
| oracle | 是（全局真值，标注为上界，不喂学习） | routing.py:188-190 |

**结论**：仓库里 **18 个 profile 全部使用 policy: hop**，而 hop 完全不消费邻居状态——
**这解释了为什么「到达时刻对齐」的机制在此前的实验里根本没有机会显现**：决策与邻居状态无关，任何状态注入都不会改变动作。

**E3 的正解**：改用 **policy: capacity**（确定性、信息受限、消费 cache 中的邻居队列广告），
它同时满足反事实机制对确定性路由器的硬性要求（algorithm = none）。

### 11.2 注入点的可实现性

cache payload 的两个关键字段（control.py:103,106）：**isl_queue_bits** 与 **isl_propagation_s**，均为 {方向: {peer, value}} 结构。
capacity 的代价为 c + qb/rate，其中 qb 在 a==sat 时取本星队列、否则取 cache 广告值（peer 不匹配或 TTL 过期即 inf）。

| 组 | 注入内容 | 平台是否已记录 | 可实现性 |
|---|---|---|---|
| O0 | 已实际收到的缓存原值 | ✅ observation_at_start.neighbours[*].advertised_isl_queue_bits | 可直接用（事实运行） |
| O1 | 相同字段在**当前时刻**的真实状态 | ✅ truth_at_commit | 可分析侧注入 |
| O2-F / O2-A | **共同未来**时刻真值 | ❌ **未记录** | **需平台新增记录**（或从 timeline 重建该时刻状态） |
| O3 | 各候选**自身到达时刻**真值 | ✅ truth_at_target | 可分析侧注入 |
| O4 | 最小代价动作（评估器） | 由逐候选反事实后果表给出 | 需多次重放 |

### 11.3 对主比较的影响（必须向 owner 说明）

任务书的主指标是 **Regret(O2strong) − Regret(O3)**，而 **O2（共同未来）真值当前未被平台记录**。
因此在本平台现状下：

- **可立即执行**：O0 vs O1 vs O3 的配对反事实比较（外加 O4 作为后悔值基准）；
- **暂不可执行**：以 O2strong 为主对照的主指标——需先补「共同时刻真值」的记录能力（属平台侧小改动，但要动内核记录面，需谨慎并单独评审）。

**因此 E3 的首轮应定位为探索性诊断**（O0/O1/O3），并在结论里明确：
主指标（含 O2strong）的确认性比较**要等共同时刻真值可用之后**，否则等于把最强的对照换成了较弱的对照。
