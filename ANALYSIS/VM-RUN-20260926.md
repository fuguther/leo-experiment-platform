## 4. 跨环境一致性:哪些相同、哪些不同（重要）

把 VM 与本地两份产物逐字段比较:

| 字段 | VM == 本地 |
|---|---|
| `pre_branch_identity` | ✅ 相同 |
| `post_branch_divergence` | ✅ 相同 |
| `candidates` | ✅ 相同 |
| `action_cost` | ✅ 相同 |
| `branch` | ✅ 相同 |
| `source.config_sha256` / `source.code_sha256` | ✅ 相同 |
| `pairing.baseline_branch_fingerprint` | ❌ **不同** |
| `pairing.branch_states_identical` | ✅ 两侧都为 true |

成本/压力探针的算力争用数字也逐位相同:`load_high_compute_1` 的
`wait_total = 17.234256 s`、`queued = 25`、`decisions = 84`,两台机器一致。

**为什么指纹会不同?** 直接对比两边的决策行(`default=str` 规范化后的 JSON):

```
决策行数            3 == 3
叶子值总数          1199
不同的叶子值        6
其中纯浮点末位差异  6   (相对误差 <= 1e-9)
结构性差异          0
例: candidate_truth.E.distance_km  本地 11979.418391153791  vs  VM 11979.418391153793
```

**结论(必须随指纹一起转述)**:`branch_fingerprint` 哈希的是决策行的**浮点字面量**,
而几何量在不同 numpy 版本下会有 1 ULP 级差异。因此:

- **指纹不可跨环境比较**——同一配置在本机与 VM 上必然得到不同的指纹字符串;
- 配对证明依赖的是**同一次运行内基线与强制跑的两个指纹相等**,这一点两环境都成立且都报告 `true`;
- 任何"把 VM 的指纹与本机指纹对照"的用法都是错的。本文件登记这条,以免后被误用。

## 5. VM 上的测试套件（如实）

在 VM 的部署树上直接跑平台测试时,**收集期就报错**:

```
ERROR ANALYSIS/tests/test_document_governance.py
!!!!! Interrupted: 1 error during collection !!!!!
```

原因不是本轮改动:VM 工作区是**父研究仓 + 平台 CODE 覆盖**,它的 `ANALYSIS/tests/` 里有
`test_document_governance.py` / `test_paired_analysis.py` / `test_workspace_hygiene.py`
三个**属于父仓、不属于平台**的测试,其中治理测试需要父仓的 `ANALYSIS/DOCUMENT-STATUS.json`,
而该文件在被部署的源根里不存在。平台仓库自己的 `ANALYSIS/tests/` 不含这些文件(CI 跑的是平台仓库)。

范围收窄到 `CODE/leo_sim/tests CODE/experiment_platform/tests CODE/tests`(平台自己的三棵
测试树)后仍然 **3 failed, 1005 passed, 1 skipped**(18m24s)。三条失败已逐条定位:

| 失败 | 失败原文 | 归因 |
|---|---|---|
| `test_receipt.py::test_strict_receipt_verify_still_rejects_different_runtime_identity` | 依赖 git 跟踪状态 | 部署树**没有 `.git`** |
| `test_stale_authorization_guard.py::test_no_tracked_authorization_binds_the_current_code_identity` | `Command '['git','ls-files','*authorization.json']' returned non-zero exit status 128` | 同上:部署树不是 git 工作区 |
| `test_stale_authorization_guard.py::test_the_superseded_authorization_is_refused_by_the_platform` | 断言 `"artifact hash mismatch"`,实际触发的是 `"matrix manifest cells do not derive from request"` | 部署树是**父仓的 `EXPERIMENTS/` + 平台的 `CODE/` 覆盖**,该实验实例的内容与平台仓库里的不同,于是**另一条**拒绝条款先触发 |

**三条都不是本轮引入的**:同样的三个测试文件在平台仓库的本地检出上全部通过
(全量 `1020 passed, 1 skipped`)。两条失败的根因是**部署形态**(rsync 出来的树没有版本控制),
第三条的根因是**部署形态**(父仓的实验实例 ≠ 平台仓库的实验实例)。

**"VM 上全套测试通过"这句话在父仓+覆盖这种部署形态下不成立**,而且这恰恰是
`CODE/work/WP-LEO-V2-PRE-EXPERIMENT-TRUST/round5/FINDINGS-VM-ACCEPTANCE.md` 记下的同一类教训的
镜像:那一轮是"本地夹具自洽 ≠ 契约正确",这一轮是"VM 环境 ≠ 平台检出"。两者都说明
**端到端必须在真机上跑一次,并且要写清跑的是哪棵树**。

## 6. 这次 VM 实跑**不能**证明什么

1. **不是正式授权运行**:没有走 `authorize_experiment`/`run-remote.sh --authorization`,
   产物没有回执、没有 `research_eligible`、不在任何信任链里。按 `03-preregistration` 的证据级别,
   它属于 **local/synthetic diagnostic**,不是 `formally governed VM`。
2. **没有覆盖任何研究性能结论**:它跑的是机制与成本的**最小诊断**,不是实验。
3. **没有在 VM 上跑过 R1–R5 的既有授权**:那些授权的 `code_sha256` 是 `0ab9bb44`,而 VM 现在
   是 `2c17718d`(§8);平台的身份闸门(`authorize_experiment.py:365`、`v2_analysis.py:560-567`)会拒绝它们。
   要在 VM 上重跑 R1–R5,必须重新 compile + authorize。
4. **没有做多节点闭环**:反事实仍是单点重放(v1 限制),不具备多卫星同时改动作的对照能力。

所以第一次的 VM 部署落后于最终提交。第二次部署把它对齐：

| | 值 |

### 8.1 VM 上重算的握手量（与本机逐位相同）

| 场景 | 基线 | 强制 | Δ送达 | 入队前工作量 | 两时刻队列变化 |
|---|---|---|---|---|---|
| `reachability`（零负载） | E → 8.91400276914237 | W → 8.91400276914237 | **0.000000000** | 0 bit | False |
| `contention`（4 Mbit 竞争包 @1 Mbps） | E → 9.941002076856767 | W → 8.326004153713564 | **−1.614997923143** | 1,566,997.9231432169 bit | **True** |
| `no_info`（真实星座，失败诊断） | N → 45.133414123234914 | S → 未送达 | —（不可比） | 0 / null | — |

`contention` 行里 **Δ送达 = −1.614997923143 s 与实测出口等待 1.614997923143 s 逐位相等**，
且该等待 = 入队前工作量 1,566,997.9231432169 bit ÷ 1 Mbps + 测量之后才加入该资源的量。
这条等式在三处独立成立：本机、VM、以及 VM 上当场算的那份摘要。

### 8.2 仍然成立的四条边界

1. **诊断，不是正式运行**：无回执、`research_eligible=false`、不在信任链内。
2. **跨环境一致性只到"报告量"这一层**：`branch_fingerprint` 仍不可跨环境比较（§4）。
3. **脚本化场景是手写拓扑**，它证明机制与度量，不证明真实星座上的路由结论。
4. **VM 上的平台测试仍有 3 条失败**，全部归因于部署形态（§5），非本轮代码。
