# 标签构造器与首个有效预测任务（2026-10-19 深夜）

## 设计（满足用户四点要求）

1. **两个时刻严格分开**：
   - `algo_query_target` = `query_targets[d]`（算法**实际查询**的时刻；hold-last 就是源测量时刻，属**过去**）；
   - `eval_target` = `eta_targets[d]`（**统一评估目标**，即候选预计到达时刻）。
   **所有方法只在这同一个 `eval_target` 上算误差**，因此 hold-last 不能拿过去的真值证明自己准。
2. **标签离线重建，不碰在线选路、不占链路资源**：
   从 `link_service_windows`（ISL、outcome=ok）取服务区间，再从 `packet_events` 的
   `queue_enter` 取每个包进入该队列的时刻，按 `(link_id, pid)` 连接
   （实测 ISL 的 link_id 文本在 queue_enter / service_start / windows 三者间**完全一致**）。
   `work_ahead(link, t) = Σ 剩余bit，遍历"入队 ≤ t 且服务结束 > t"的包`
   （已开始服务则按 `(end−t)/(end−start)` 折算，未开始则计全额）。
3. **人口场景与选路修复核验可并行**（另见 POPULATION-CHECK.md）。

## 一次被我抓到的错误（保留记录）

第一版把 `work_ahead` 写成"所有 start > t 的服务窗之和"——那是**该链路后续全部业务量**，
不是 t 时刻积压。症状很刺眼：**预测 0 bit、标签 17 916 000 bit**。
修正为"已入队且未服务完"后，同一格误差降到合理量级。**这类错误只有靠"量级荒谬"才能暴露，
所以必须先把量级检查写进验收。**

## 首个可靠结果：hold-last 在正确任务上表现很差

格 `sc-cond-r050-arm4-s111` / arm=candidate，40 000 条决策、33 904 条带标签：

| 指标 | 值 |
|---|---:|
| 标签覆盖率 | **100%（33 904 / 40 000 无缺失）** |
| `label > 0`（目标时刻确有积压） | **8 707 = 25.68%** |
| `predicted > 0` | **0 = 0.00%** |
| 在 `label>0` 子集上的 |误差| | 均值 **8 884 bit**、中位 9 232 bit |

**`predicted` 恒为 0**：hold-last 返回的是"最后一次测到的队列"，
而该测量值为 0；目标时刻（7.5 ms 后）实际已有积压的占 25.68% ⇒ **hold-last 系统性漏判积压**。

## 由此必须撤回的旧结论

> **§12.20 与 §12.41 的"hold_last 已吃掉 99.85% 可压缩量"不成立。**

原因：那两项分析把预测**与"下一条观测值"比较**（相邻决策的队列预测），
而正确的任务是**与"查询目标时刻的真值"比较**。两者不是同一个任务：
相邻观测间隔 <5 ms 且高度自相关，所以 hold_last 看起来近乎完美；
而按目标时刻取真值后，误差均值是 **8 884 bit** 量级、且系统性偏低。

**这正是用户指出的问题**——"预测离线脚本中'相邻决策队列预测'的结果，
不得继续作为'陈旧通告预测任务接近极限'的依据"。**实测证实了这一点。**

**影响**：既然 hold_last 在正确任务上并不好，**学习模型（GRU/TCN/文献方法）是否更好，
必须重新作为开放问题来测，不能再用旧的 99.85% 论断关闭它。**

## 尚未通过验收的部分（不得宣称预测数据就绪）

- `generation` 一致性：`link_service_windows` **不含 generation**，
  因此"目标时刻同一资源"的 generation 无法离线核验 ⇒ **需补日志或显式声明该限制**；
- 覆盖样本尚不完整：缺"陈旧+非恒等预测器""共同未来""空/非空/缺历史/generation 改变"的分类统计；
- 唯一键（`decision_id`+候选+查询身份）唯一性未查；
- 真值采样"事件前/事件后"的时刻约定未写明。

**结论：`build_prediction_labels.py` 可用且已暴露真实任务下的错误量级，
但"预测记录验收"尚未通过，第一格仍只能算物理/性能探针。**
