# 预热窗口对照（2026-10-14）：预声明设计

## 为什么要换设计

既有的九次更新周期扫描在 12 秒的固定时长里跑完。逐包复算显示 4 秒周期相对 0.5 秒周期新增的 638 个未达标包里 615 个（96.4%）属于前 4 秒发包。进一步核查决策记录发现原因**不是**"状态陈旧"，而是更基本的一件事：

- 4 秒周期的运行里，**t=4 之前根本没有任何 forward 决策**——节点还没有收到过任何广告，没有任何可用状态；
- 一旦第一条广告到达，候选覆盖率立刻回到 99% 以上（4 秒周期 t∈[4,5) 为 99.8%，2 秒周期 t∈[2,3) 为 100%，0.5 秒周期 t∈[0,1) 为 100%）。

所以旧曲线量的是"**没有状态**"持续了多久（≈广告周期），不是"状态有多旧"。这两件事必须分开。

## 本设计

- 时长 28 秒，广告周期 ∈ {0.5, 2, 4} 秒。
- 业务全程 [0, 24) 秒，系统是同一个物理系统。
- **预声明评估窗口：发包时刻 ∈ [12, 24)**。预热 [0, 12) = 最长广告周期的 3 倍，保证三种周期在评估窗口内都**已经收到多条广告**，比较的是陈旧程度而不是有无状态。
- D4=4 秒，最后一次发包在 24 秒，期限在 28 秒前成熟。

## 单元

- 第一阶段（R1）：stale 臂，广告周期三档，seed 7。看"状态陈旧"本身是否还有影响。
- 第二阶段（R2）：在最长的 4 秒周期上跑 now / common / candidate，与同一格的 stale 配对。

## 预声明判据

- 若 [12,24) 窗口内三档仍单调且幅度可观 → 陈旧状态本身有影响，R1 成立。
- 若三档在窗口内接近、不单调 → 旧曲线的差异主要是冷启动，R1 需要改口径重述（改为"控制面恢复期损失"而非"状态时间错位损失"）。
- 两种结局都按预声明口径记录，不在确认集上换窗口。
